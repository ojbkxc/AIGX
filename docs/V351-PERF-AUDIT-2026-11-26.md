### 审计发现但本轮未排期

- **failover 每候选深拷贝整个请求**：`api/openai/chat.rs:569,1498`、`api/anthropic.rs:853,1823` 的 `(*chat_req).clone()` 仅为改 `model`。候选 3 次 = 3 份完整对话（可达数百 KB~MB）。改 `Arc<ChatFormat>` + model 覆盖层，牵动面大，需单独一轮。
- **候选渠道列表深拷贝 3–4 次**：`channel/mod.rs:1075/1781/1786`、`api/openai/resolve.rs:444`。`Channel` 含 4 个 Vec + 2 个 HashMap；改 `Arc<Channel>` 会波及全部选路/管理面，需单独一轮。
- **Drop / 499 路径同步 BPE 计数**：`api/openai/billing.rs:815-820,1281`，纯 CPU 正则 BPE 直接堵 tokio worker；建议 `spawn_blocking` 并复用请求入口已算好的值。
- **API Key 每请求深拷贝**：`api/auth.rs:288-295` + `chat.rs:520`，`ApiKey` 含多个 Vec；建议返回 `Arc<ApiKey>`。
- **SQLite `get` 未走 blocking 池**（`src/storage/sqlite.rs:103`）：每请求约 4 次同步读抢同一把连接锁。该文件当前由并行改动占用，暂缓。
- **UsageTracker 每请求双 RMW**（`src/usage/mod.rs:73-127`）：与 `dailyagg` 重复记账，且 `legacy_kv_sweep` 已把相关键当遗留清理。涉及报表数据源切换，需单独确认。
- **启动 N+1 加载**（`src/main.rs:298-372`、`account_session/store.rs:394-421`）：`list` + 逐 key `get`，可改范围扫。
- **日志读接口全前缀兜底**（`src/log/mod.rs:1182,1295,1390,...`）：无命中时 `list("reqlog:")` 全量物化。
- **`/v1/messages` 首帧前阻塞式 prompt 计数**（`api/anthropic.rs:1271-1275`）：TTFB 被整段 tokenize 拖慢。
- **plugin Wasm 无界 channel**（`bridge/plugin.rs:291`）：客户端消费慢时内存无界。
- **续写暂存上限漏算 tool 参数**（`continuation.rs:465-474`）：`estimate_chunk_bytes` 只算 content/reasoning，1 MiB 上限可被绕过。
- **image_compat 无总 body 上限**（`image_compat/mod.rs:407-431`）：多图时峰值内存随图数线性增长。
- **SeaORM 索引**：`request_logs` 缺 `request_id` 索引与 `(user_id, created_at)` 复合索引（当前 `db_conn` 仅建连未查询，属潜在项）。

## 3. 结论

- 前端首屏与路由切换开销已实质下降（英文首屏 gzip −30.6%，Gateways −81%）。
- 后端最高收益的三条是「每请求读 /proc」「选路写锁」「每请求深拷贝对话/渠道」，前两条本轮处理，第三条需要一轮专门的重构（`Arc` 化），不宜与其他改动混在一起。
