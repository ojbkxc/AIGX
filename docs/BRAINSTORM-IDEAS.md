# AIGX 头脑风暴清单（原创增强点）

> 第一阶段提案文档 · 2026-09-07
> 定位：参照项目（new-api / open-webui）之外的原创增强点，围绕 AIGX 独有优势（Rust 性能红利、调度智能深度、缓存+token 估算、GraphQL）。
> 每项标注：为什么（why）→ 形态（what）→ 分期（when）。本清单在每轮迭代中持续扩充。

## A 类：Rust 性能红利（new-api 做不到的）

### A1. 实时渠道竞速（hedged request）
- **为什么**：AIGX 调度路径无 GC 抖动，可安全地同时向 2–3 个渠道发起相同请求，首个 token 到达即胜出，取消尾请求。Go 做这件事的成本与 tail latency 抖动更高。
- **形态**：`channel/` 新增 `hedge` 策略（与现有 priority/weight/affinity 并列），配置化（默认关闭，按模型开启），含取消尾请求、超时与故障注入测试。
- **分期**：P2（已在路线图）。

### A2. 毫秒级 failover 看板
- **为什么**：AIGX 已有断路器/AIMD/亲和路由/响应质量评分的深度数据，但目前只在后端内存中，前端看不到。
- **形态**：`/api/dashboard` 新增「渠道实时状态」——每渠道延迟分布、熔断状态、AIMD 当前值、failover 次数；前端 NetworkLayer 页面升级为「调度实时地图」。
- **分期**：P1。

### A3. 渠道自动调参
- **为什么**：AIMD 的参数（增长/衰减系数）目前是常量，但渠道特征不同（有的稳、有的抖）。
- **形态**：AIMD 参数按渠道统计特征自动拟合（在线 EWMA 学习），保留人工覆盖。
- **分期**：P2。

### A4. 故障自愈时间线
- **为什么**：运营人员最想知道「这个渠道昨天为什么挂过、自己怎么恢复的」。
- **形态**：断路器状态变更事件流（环形缓冲）→ 管理面板时间线视图（已有时长轴组件可复用）。
- **分期**：P2。

## B 类：缓存与成本透明

### B1. 缓存命中省钱看板
- **为什么**：AIGX 有响应缓存 + cache_price 字段，但命中省下的钱对用户不可见。
- **形态**：仪表盘新增「缓存节省」卡片（命中次数 × cache_price 差值），与请求日志 `cache_hit` 标记联动。
- **分期**：P1（与后端「缓存命中差异化计费」同批落地）。
- **状态**：✅ 已落地（2026-09-08）。后端 `GET /api/dashboard/cache_savings` 聚合
  `cache_hit` 日志返回 `hit_count` / `cache_tokens` / `billed_cost` / `saved_estimate`；
  前端仪表盘「缓存节省」卡片展示节省估算与命中统计。`saved_estimate` 按当前定价表
  `input_price` 估算差价，定位为运营感知而非审计账本。

### B2. 请求前成本预估器
- **为什么**：token 估算能力已存在（`token_estimate.rs`），new-api 无此体验。
- **形态**：Playground/聊天输入框下方实时显示「预计消耗 ≈ ¥x.xx」，发送前可见；管理端定价页有「成本模拟器」。
- **分期**：P1。

### B3. 跨渠道价格仲裁
- **为什么**：同一模型多家上游价格不同，当前调度只看可用性不看成本。
- **形态**：调度新增「价格感知」维度（可选开关）：同级渠道间把价格纳入加权，允许「更便宜优先」与「更快优先」两种模式。
- **分期**：P2（需先完成 B2 的定价数据完备化）。

## C 类：调度智能的运营化

### C1. 渠道「健康档案」
- **为什么**：连通性测试只给瞬间结果，运营需要趋势。
- **形态**：每渠道持久化健康事件摘要（最近 30 天：成功率、P95 延迟、熔断次数），页面渠道行展开可见。
- **分期**：P1（复用现有 `health_manager`）。

### C2. 调度决策回放
- **为什么**：用户投诉「为什么我的请求走了这个渠道」时，运营需要可解释性。
- **形态**：请求日志记录调度决策链（候选集 → 过滤原因 → 选中渠道），管理端可展开查看。
- **分期**：P1（日志字段扩展，向后兼容旧日志）。

## D 类：GraphQL 与数据能力

### D1. GraphQL 灵活查询面板
- **为什么**：AIGX 已有 GraphQL 模块（`src/graphql/`），new-api 没有。把内部能力暴露给管理端是零成本超额收益。
- **形态**：管理端新增「数据查询」页面（只读 GraphQL 查询 + 结果表格/JSON），权限限定 admin/auditor。
- **分期**：P1。

### D2. 用量数据 API 化（用户侧）
- **为什么**：普通用户当前只能看钱包余额，看不到自己每个模型的用量分布。
- **形态**：用户侧「用量」页（按模型/日聚合，复用 `/api/usage/*` 的查询逻辑加用户维度过滤）。
- **分期**：P1。

## E 类：协议与计费的超前想象（第九章精神）

### E1. 意图层路由（5–10 年形态）
- **为什么**：模型路由终将从「按名字匹配」进化为「按任务特征匹配」——短问答走便宜模型，长推理走贵模型，Agent 走工具模型。AIGX 已有 `semantic/` 模块（embedding 相似度路由）雏形。
- **形态**：`SemanticRouter` 从「示例匹配」升级为「意图分类层」：prompt 特征向量 → 路由规则（成本/延迟/能力约束组合），规则可配置、可观测、可回放。
- **分期**：P2 立项（先完成 C2 决策回放，再引入意图层，保证可解释）。

### E2. 微支付流计费
- **为什么**：AI 调用天然是「按 token 微计费」，现在的「预充值扣余额」只是过渡形态。
- **形态**：配额支持「按次结算」模式（与预留/结算两段式计费同构），为未来轻量支付通道预留 trait 边界（`BillingSink` 抽象）。
- **分期**：P2 末（先在 P1 完成预留/结算，不动支付通道）。

### E3. 渠道即数据源（模型观测）
- **为什么**：网关天然看到所有上游的延迟/质量/价格，这是任何单一供应商都拿不到的全景数据。
- **形态**：`/api/dashboard` 输出「模型-渠道」观测矩阵（价格/延迟/成功率三维），供自动调参与渠道采购决策。
- **分期**：P2（A2/A3 的数据基础）。

## F 类：被否决的炫技方向（记录在案）

| 方向 | 否决理由 |
|---|---|
| 语音聊天（自建 STT/TTS 全链路） | 依赖浏览器能力即可满足，自建是架构堕落 |
| 协作空间（多人共享会话） | 单机网关的产品边界之外 |
| 插件市场 | 会引入不可审计的执行环境，与百年工程红线冲突 |
| AI 生成 UI 配置 | 不可预测的输出不属于「保守而正确」的技术选型 |

## 2026-09-08 二轮批判式审查（以 P1 已落地代码为靶子）

> 本轮不再「提出新点子」，而是**对着已落地的 P1 代码找弱点**：凡是发现的问题都给出更优方案。
> 状态标记：✅ 已验证落地 | ⚠️ 发现疑点待修 | 💡 更优方案提案

### G1. 预留/结算的一致性缺口（✅ 已落地 2026-09-08）
- **发现**：`reserve_usage()`/`settle_usage()` 只挂在 OpenAI chat/completions 链路，**新落地的 `/v1/rerank` 仍走旧式 `charge_usage()` 事后计费**（`src/api/openai.rs:2870` 附近），同一数据面内计费语义分裂。
- **更好方案**：P1 收尾前把 rerank 切换为一致的「预估 → 预留 → 结算」路径。理由：rerank 的 prompt token 可精确估算（文档内容全在请求里），预留偏差小；保持两条计费语义并存会让 2126 年的维护者困惑「为什么同一文件里有两套扣费」。
- **建议动作**：P1 第二波清单加一项「rerank 计费对齐」。
- **附加发现（🔴 疑似 bug）**：`reserve_usage()` 的 key 预留失败回滚分支把 `settle_quota(uid, reserved_user, 0)` 当「释放」用——语义上是 release 而非 settle，且 `settle_quota` 内部有 `reserved.min(user.reserved_quota)` 的钳制；当同一用户并发请求都持有预留时，这个钳制可能**归还别人的预留**。建议加 `release_quota()` 专用方法并把回滚改为 release 语义，附带并发测试（两个 key 同时预留同一用户）。

### G2. 预留冻结没有「解冻超时」（✅ 已落地 2026-09-08）
- **发现**：`User.reserved_quota`/`ApiKey.reserved_quota` 是裸字段，无过期时间。若进程在 `reserve` 后、`settle` 前崩溃（或流式请求挂死），预留额度**永久冻结**，用户余额被无声吃走。
- **更好方案**：预留记录携带 `reserved_at` 时间戳（不破坏 JSON 兼容，加 `#[serde(default)]`）；cron 已有 `src/cron.rs` 调度器，加一个「预留回收」周期任务（TTL 建议 30 分钟，远超 max_tokens 请求上限），只解冻超时未结算的预留。
- **建议动作**：P1 第二波与 rerank 对齐合并为「计费闭环完整性」。

### G3. TOTP 的「secret 持久化」只有一个副本（💡 更优方案）
- **发现**：TOTP secret 以明文 base32 存在 User 记录里，备份/恢复场景下用户会看到自己的 secret 明文（可被截图泄露），且**无恢复码机制**——用户换设备即锁死。
- **更好方案**：生成 10 个一次性恢复码（SHA-256 哈希存储，展示一次即删），登录页 TOTP 输入框支持恢复码。这是 open-webui/new-api 都缺的原创细节，成本约 150 行纯函数。
- **建议动作**：P2 或作为 TOTP 收尾的顺带项。

### G4. 缓存命中计费的记账维度残缺（✅ 已落地 2026-09-08）
- **发现**：缓存命中按 `cache_price` 计费后，`usage_tracker.accumulate(prompt_tokens, completion_tokens, 0, 0, 0, 0.0)` 仍把命中当「正常输入」，没有走 `cache_read` 维度；请求日志 `error_msg = "cache_hit"` 也无法与普通请求区分开统计。
- **更好方案**：`accumulate` 的 cache_read 参数已存在但没被使用——命中时应 `accumulate(0, 0, 0, prompt_tokens, 0, 0.0)`，日志加 `cache_hit: bool` 字段（向后兼容）。
- **建议动作**：P1 第二波「缓存节省看板（B1）」的前置修正，否则省钱看板拿不到准确数据。

### G5. 失败路径的预留不释放（🔴 疑似 bug）
- **发现**：非流式 chat 的失败路径（`reservation` 已建立但渠道全部失败、返回 502）只在日志里 `record_request`，**未看到 settle/release 调用**——预留被永久冻结（与 G2 同族，但这是每条请求必然触发的确定性泄漏）。
- **更好方案**：失败路径统一 `settle_usage(..., 0, 0, None)` 或 `release_quota()`；配合 G2 的预留 TTL 双保险。
- **建议动作**：P1 第二波必做，附带「失败不冻结」集成测试。

### G6. cron 框架的「单任务独占协程」伸缩性（💡 更优方案）
- **发现**：`src/cron.rs` 每个任务一个独立协程（当前 2 个任务没问题），但 P1 收尾会加预留回收、模型同步等任务，若上百任务会变协程海。
- **更好方案**：P2 再评估是否合并为「单协程多任务 tick 表」（任务 ≤20 时保持现状，不提前优化）。记此条是为 2126 年的维护者留下「为什么不合并」的答案。
- **建议动作**：无（仅记录决策理由）。

### G7. 待确认的「更优方案」：hedged request 的优先序（💡）
- **发现**：ROADMAP 把 A1 竞速排在 P2，但 P1 已落地的「响应质量评分 + 亲和路由 + AIMD」让竞速的收益已经具备——竞速是「更快」的质变，不是锦上添花。
- **更好方案**：把 A1 提前到 P1 末或 P2 首，且做「价格感知竞速」（B3）——竞速时同时下注便宜渠道和快渠道，首 token 胜出后取消尾请求，把 A1 与 B3 合并实现，避免二次动调度核心。
- **建议动作**：ROADMAP P2 目标 1 与 7 合并标注。

### G8. 待确认的「更优方案」：Rerank 计费按字符而非 token（💡）
- **发现**：rerank 上游（Cohere/Jina）普遍按「搜索单元」或字符计费，AIGX 现在按 prompt token 计费，模型定价表若没有 rerank 模型条目会 `ensure_model_priced` 拒绝——运营者必须手工加条目。
- **更好方案**：rerank 支持独立的 `rerank_price` 定价维度（按文档字符数 × 单价），fallback 到 token 计费；否则新模型接入体验断裂。
- **建议动作**：P1 收尾或 P2。

### G9. 已否决项确认（无动作）
- MJ-Proxy / Suno / 违规罚金 / ClickHouse / 插件市场：维持否决，理由不变。
- Workspace_B780A2 分支暂不接入两段式：**认同**（爆炸半径最小化），但需在 ROADMAP 记录「该分支的计费语义落后主链路」的技术债条目，P2 清债。
